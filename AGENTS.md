# Next.js Agent Rules

This project may use a newer or modified version of Next.js than your training data.

Before writing or changing Next.js code, inspect the installed Next.js version and read the relevant documentation in:

node_modules/next/dist/docs/

The installed project and its local documentation are the source of truth.

## Core Rules

1. Inspect the existing code before making changes.
2. Preserve existing functionality.
3. Make the smallest safe change that completely satisfies the request.
4. Do not rewrite working code unnecessarily.
5. Do not replace real functionality with demos, mocks, placeholders, or fake implementations.
6. Do not assume APIs or conventions from older Next.js versions.
7. Follow the installed Next.js version and its local documentation.
8. Preserve the existing project architecture unless a migration is explicitly requested.
9. Do not modify unrelated files or functionality.
10. Verify changes before considering the task complete.

## Next.js Version

Before implementing a Next.js-specific feature:

- Check `package.json`.
- Check the installed Next.js version.
- Inspect the relevant documentation under `node_modules/next/dist/docs/`.
- Check for deprecations and breaking changes.
- Follow the installed version's API and conventions.

Never rely only on prior knowledge of Next.js.

## Existing Architecture

Respect the project's existing:

- App Router / routing structure
- Server Components
- Client Components
- Route Handlers
- Server Actions
- API routes
- Authentication
- Authorization
- Database layer
- Prisma configuration
- Middleware
- Styling system
- State management
- Utility functions
- Component structure

Do not migrate technologies unless explicitly requested.

## Server and Client Components

Use Server Components by default when appropriate.

Only add:

"use client";

when client-side functionality actually requires it.

Do not unnecessarily convert Server Components into Client Components.

Never expose server-only secrets or private environment variables to the browser.

## Authentication

Preserve all existing authentication and authorization behavior.

Never:

- Bypass authentication
- Bypass authorization
- Hardcode credentials
- Expose passwords
- Expose authentication secrets
- Create an admin bypass

Sensitive operations must remain protected on the server.

## Database

If the project uses Prisma or another database:

1. Inspect the existing schema first.
2. Understand existing relations.
3. Reuse existing database utilities.
4. Avoid duplicate models.
5. Do not silently change existing data behavior.
6. Do not hardcode database credentials.
7. Make the smallest safe schema change when required.

## Environment Variables

Never hardcode:

- API keys
- Database URLs
- Authentication secrets
- Payment credentials
- Email credentials
- Cron secrets
- Third-party credentials

Use environment variables and keep server-only values server-side.

## UI Changes

When the user asks for a UI change:

- Preserve existing functionality.
- Preserve existing routes.
- Preserve existing APIs.
- Preserve existing state.
- Preserve authentication.
- Preserve database behavior.
- Preserve responsive behavior.

If the user says "same UI", do not redesign.

If the user says "only fix", only make the requested fix.

If the user says "make it premium", improve:

- Spacing
- Typography
- Visual hierarchy
- Alignment
- Responsiveness
- Accessibility
- Component states

Do not add unnecessary gradients, animations, colors, or redesigns.

## Styling

Follow the project's existing styling system.

If the project uses Tailwind CSS, continue using Tailwind.

If it uses CSS modules, continue using CSS modules.

If it uses global CSS, preserve that approach.

Do not introduce a new CSS framework for a small change.

## Components

Before creating a new component:

1. Search for an existing component that already performs the same function.
2. Reuse it when appropriate.
3. Follow the existing naming and folder conventions.
4. Avoid duplicate components with identical functionality.

## Forms

Preserve:

- Validation
- Error handling
- Loading states
- Submit behavior
- Server-side validation
- API/database integration
- Accessibility

Never rely exclusively on client-side validation for security-sensitive operations.

## API and Route Handlers

Before changing an API:

- Inspect the existing endpoint.
- Preserve its contract when possible.
- Preserve authentication.
- Preserve authorization.
- Validate input.
- Handle errors correctly.
- Avoid exposing sensitive information.

Do not silently break existing consumers.

## File Uploads

For upload functionality:

- Validate file type.
- Validate file size.
- Do not trust client-provided filenames.
- Prevent unsafe file paths.
- Preserve existing upload behavior.
- Update the UI correctly after upload.
- Do not expose private files unintentionally.

## Accessibility

Maintain:

- Semantic HTML
- Proper labels
- Keyboard navigation
- Visible focus states
- Appropriate ARIA attributes
- Accessible buttons and links
- Sufficient color contrast

Prefer `<button>` and `<a>` over clickable `<div>` elements.

## Responsive Design

All UI changes must remain usable on:

- Desktop
- Laptop
- Tablet
- Mobile

Check:

- Overflow
- Navigation
- Forms
- Tables
- Modals
- Buttons
- Cards
- Headers
- Sidebars

Never fix desktop by breaking mobile.

## Performance

Avoid unnecessary:

- Client Components
- JavaScript
- Network requests
- Database queries
- Re-renders
- Dependencies

Use the installed Next.js capabilities appropriately.

Do not introduce complex optimizations without a real need.
